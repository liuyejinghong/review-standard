# review-standard

> 实战工坊 / [Field Lab](https://github.com/liuyejinghong/field-lab) 的一部分：在真实项目里做出来、持续打磨的 AI Agent 工具。

A code review standard written for AI agents. It tells a coordinating agent how to grade the risk of a change, how many independent reviewers to send and what each should trace, which findings are worth reporting, how to verify them, and when to stop. It has two modes: reviewing a change (a diff, a PR, a sub-agent's delivery) and auditing an existing codebase with no diff. It is a set of Markdown instructions, not a program, and it does not prescribe any model. The measured data behind it comes from one project and a small sample; thresholds are starting values.

---

给 AI Agent 用的代码审查标准。主控 Agent 按它决定：这次审查值得花多少力气，派几位审查者、各自查什么，哪些问题才算发现，发现怎么核实，什么时候停。

它是几份 Markdown 说明，不是程序，没有依赖。可以装成 Claude Code skill，也可以让任何 Agent 直接读。

## 解决什么问题

让 Agent 审查代码时，常见的情况有四种：

- 所有改动都用同样的力气审。改一行注释和改下单逻辑走同一套流程，前者浪费，后者不够。
- 审查者报告一堆命名和格式意见，真正会出错的地方埋在里面。
- 审查者说“没问题”就放行，或者审查者报的问题没人核对就要求返工。
- 修一次审一次，没有停下来的规则，也不知道花了多少 token。

本标准对这四件事各给了一套固定做法。

## 两种模式

按审查对象选模式，不按谁发起选。

| 模式 | 审查对象 | 适用场景 | 结果 |
| --- | --- | --- | --- |
| 改动审查 | 有明确改动范围：diff、PR、提交区间、子代理交付 | 合并前把关；验收子代理写的代码；审修复 | 放行判断：`APPROVE`、`REQUEST_CHANGES` 或 `INCOMPLETE` |
| 存量审查 | 项目、目录、模块或文件，没有改动基线 | 接手别人写的项目；审计代码库；找存量问题 | 发现清单、每个模块的风险等级与覆盖状态、整改顺序。不给放行结论 |

## 核心做法

### 流程概览

改动审查：

```
分级 ──► 前置步骤 ──► 派发审查者 ──► 去重与核实 ──► 结论 ──► 复审（需要时）
L0–L3    检查、过滤、   按等级定人数    另一位尝试      三种      按修复范围
         拆分、任务书   与分路          证伪            之一      决定审多少
```

存量审查：

```
摸底 ──► 定重点 ──► 分批派发审查者 ──► 去重与核实 ──► 发现清单与整改顺序
项目地图  给模块排序   高风险模块派两路                   列出没审的模块
```

### 按风险分级

主控用确定性信号把改动分成四级，不靠模型判断。

| 等级 | 改动 | 审查力度 |
| --- | --- | --- |
| L0 机械 | 生成物、格式化、纯重命名、文档 | 1 位审查者，只核对“确实是机械改动” |
| L1 普通 | 局部行为变更，不碰高风险面 | 1 位非作者，审一遍 |
| L2 高风险 | 碰到高风险面 | 2 位非作者，互相独立 |
| L3 阶段节点 | 一个阶段或特性整体合入前；跨 3 个以上模块的重构 | 3 路并行 |

高风险面由项目自己声明。项目没有声明时用默认清单：外部副作用、持久化与迁移、并发、跨进程合同、认证授权、恢复路径、身份与幂等。拿不准时取较高等级。

### 分路与隔离上下文

- 审查者不能是写这段代码的那个实例。每位审查者从全新的上下文开始，互相看不到对方的结果。
- 高风险改动必须有一路做“合同追踪”：沿项目的不变量和接口合同走调用链，对每个外部调用逐个走通成功、失败、结果未知、重复响应四种返回。另一路看业务流程和“这段代码有没有必要”。
- 分路只决定各自深挖什么。每位审查者都要读完全部变更行，看到别路的问题也要报。
- 审查是只读的。审查者不改代码。

### 发现的准入

一条发现必须给出可达的失败场景（什么输入或状态，导致什么错误结果），或者可度量的代价（哪个指标，前后数值）。写不出来的不报。命名偏好、格式意见、表扬和纯提问都不算发现。

审查覆盖 8 个维度：正确性、合同与不变量、职责与模块边界、必要性、隐藏兜底、重复与死代码、测试质量、对后续 Agent 的可读性。每个维度都写明了什么值得报、什么不报。

每条发现用固定格式，区分“已走通触发路径”和“路径成立但有一个前提没核实”，并分四档严重度：阻断、阻断待核实、应改、可选。

### 核实

严重的发现要交给另一位没有参与报告的核实者。核实者的任务是证伪：找出让失败场景不可能发生的代码或成文规则。只删除被证明错误的发现；既证不了真也证不了假的保留，并写明缺什么前提。

### 三种结论

- `REQUEST_CHANGES`：有已成立的阻断发现。
- `INCOMPLETE`：有文件没审到、被截断，或有阻断级发现还没裁决。
- `APPROVE`：其余情况。

单个审查者说 `APPROVE` 不算放行。放行由主控依据全部发现、核实结果和作者的实现报告决定。

### 复审

- 修复没碰高风险面：1 位审查者，只看修复本身、原问题是否关闭、修复带来的新接触点。
- 修复碰到高风险面：不降级，仍然包含合同追踪。
- 修复改动很大，或改了接口：当作新改动重新分级。
- 追加一遍没有新的确认发现就停。全量审查一般不超过 2 遍。

### 记账

每次审查记录三个数：峰值上下文、累计新输入、缓存读取。数字从会话记录的 usage 字段取，不用工具界面汇报的单个值，后者可能只是最后一次请求的大小。

## 安装

作为 Claude Code skill 使用：

```bash
git clone https://github.com/liuyejinghong/review-standard.git \
  ~/.claude/skills/review-standard
```

也可以把整个目录复制到 `~/.claude/skills/review-standard/`。Claude Code 会自动发现它，不需要其他配置。

用其他 Agent 时，克隆到任意目录，让 Agent 读 [`SKILL.md`](SKILL.md) 即可。

## 使用

对主控 Agent 说：

- 审一次子代理交付：“用 review-standard 审查刚才子代理提交的改动，实现报告在 `<路径>`。”
- 审一个 PR：“用 review-standard 审查 PR #123。”
- 接手一个项目：“我刚接手这个项目，用 review-standard 做一次存量审查，先审高风险模块。”

存量审查不会逐行读完整个仓库。它先给模块排序，再分批审，没审到的模块会明确列出。最好在开始时说明范围或预算。

文件说明：

| 文件 | 内容 | 谁读 |
| --- | --- | --- |
| [`SKILL.md`](SKILL.md) | 完整标准 | 主控 Agent |
| [`templates.md`](templates.md) | 审查、存量审查、复审、核实四种任务书模板 | 主控派发审查者前读 |
| [`evidence.md`](evidence.md) | 每条规则的依据与证据强度、否决的做法、待校准项 | 想知道“为什么这样定”的人 |

项目自己的规则（`AGENTS.md`、`CLAUDE.md`、合同文件）优先于本标准。两者冲突时按项目规则。

## 与其他工具的关系

- **内置 `/code-review`**：不替换。它可以作为 L1 的正确性审查引擎，它报的阻断级问题同样要核实。其余维度仍由审查者负责。
- **`/simplify`**：审查中不调用，因为它会直接改代码，而审查是只读的。“没必要”和“重复”类的发现成立后，再决定是否用它修。
- **结构度量工具**：例如 Python 项目可用 [maintainability-scorecard](https://github.com/liuyejinghong/maintainability-scorecard)。项目配置了这类工具时，较大的改动和存量审查会运行它，审查者用它给出的数字，不自己估算。没有配置时记“未设置”，不要求为此新建工具。指标变差本身不算发现，要定位到具体代码才报。

## 不规定模型

标准只规定岗位：主控、审查者、核实者，以及“审查者不能是作者”。用哪个模型、几档推理强度，由你的项目配置决定。唯一的要求是合同追踪那一路用项目允许的最高常规档，并且不为省 token 调低。

## 证据与局限

每条规则的来源都列在 [`evidence.md`](evidence.md)，并标了证据强度：公开研究或源码核对、厂商说法、作者项目实测、推断、估算。

使用前要知道的局限：

- 作者的实测数据来自单一项目的单一特性，共 8 轮审查。样本小，不能当作普遍结论。
- 存量审查模式的规则全部是推断，还没有实测。
- 各项数字（约 400 行的拆分界线、复审的 30% 界线、对照轮次数等）是起步值，要在你自己的项目上校准。
- 高风险改动目前有两种编排并存，对照数据攒够后才会保留一种。
- 节省 token 的幅度都是估算，没有实测。

完整清单见 `evidence.md` 的“待校准项”和“开放问题”。

## 迭代与贡献

标准会随实测数据修改。欢迎提 issue 或 PR，最有用的是：

- 你在自己项目上的对照数据：两种编排各发现了多少真问题、多少误报、花了多少 token。
- 审查漏掉、事后才暴露的真问题，以及它属于哪一类。
- 某条规则在你的项目里行不通的具体情况。

修改规则时，请同时在 `evidence.md` 写明依据和证据强度。没有依据的阈值标为起步值。
